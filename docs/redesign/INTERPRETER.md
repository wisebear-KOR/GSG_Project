## 4. 열린 것

| # | 열린 것 | 선택지 |
|---|---|---|
| O1 | **1단계 질문의 꼴** | ⓐ 일마다 "해야 하는가?" 예/아니오 12 + "금하는가?" 예/아니오 12 (24줄, 정답 붙이기가 가장 단순 — 석판 사례의 `forbid:` 정답을 쓴다, 둘 다 "예"인 모순은 규칙으로) · ⓑ 일마다 "하라 / 하지 마라 / 말하지 않음" 12 (같은 정보를 절반 줄로, 모순 없음 — 의견: 이것을 권함) · ⓒ 예/아니오 12 + 금지는 석판 규칙 (은유적 금지를 놓침). 어느 쪽이든 **"하라" 확률 순으로 행동 수만큼 채운다** — "가장 먼저 할 일"·"남는 손" 질문은 따로 두지 않는다. 계시의 성격은 4지선다 하나 |

| O3 | 2단계에서 **채운 손의 칸** | Kev가 꼭 고른다 ("곳을 말하지 않음" 없음) / 기본값(D5)에 맡긴다 |
| O4 | "모자란 것"을 상태에 넣나 | §2 |
| O5 | 질문 글의 언어 | 영어 (Kev가 배운 말) / 한국어. 계시는 한국어 그대로 |
| O6 | 확신도가 낮을 때 | 석판으로 넘김 / 대사제가 "말씀이 흐릿하다" |

## 5. 2단계 — 어디서 (초안)

- 상태: 칸 이름이 붙은 사실 — 우리 수도·마을, 율법파 수도·마을·성벽, 성지, 율법파의 뜻("C4에 마을을 지으려 한다"), 붙인 이름.
- 질문: 뽑힌 일마다 "이 일을 어느 칸에서 하라는가?" — 선택지는 **그 일을 할 수 있는 칸만**, 글은 `C4: 평원`처럼 이름과 지형만. **수확량·활성도는 넣지 않는다** (값이 새지 않게 — Kev가 기름진 칸을 알아서 고르지 못하게).
- 석판에 남는 것: 정확한 지목(칸 이름 "E4", 붙인 이름, "E4 말고"), 수의 말("두 곳", "모두"), 활성도 낱말("기름진 곳", "쉬던 땅") — 글자 맞춤이라 규칙이 확실하다.
- 수의 말이 있으면 같은 칸 질문의 2순위까지 가져간다.

| 안 | 버린 까닭 |

## 7. Kev의 입출력 (요약)

- 요청: `{ state, questions: { 이름: { type, instructions, criteria } } }`. `state`는 문자열이나 JSON (객체는 `키: 값` 줄로, 배열은 `- 항목` 줄로 편다).
- 질문 종류: `noul` (예/아니오, 답은 예의 확률) · `choice` (1~255 선택지 중 하나, 확률 분포·1순위·확신도) · `score` (순서 있는 등급, 기댓값 등급·분포·확신도).
- 질문끼리는 서로를 보지 않는다. 한 질문은 하나만 고른다 (여럿은 `noul`을 항목마다). 선택지 순서가 답을 바꿀 수 있다 (`/v1/systemone/permute`).
- 속: Qwen3.5 바탕에서는 질문마다 "상태 + 그 질문"을 한 줄로 보통 순서대로 돌리고 (`rows_of`), `<decide>` 자리와 각 `</opt>` 자리의 은닉 상태를 작은 판정 헤드(차원 → 256 두 행렬의 내적, 온도 보정)로 견준다. 특수 토큰은 Qwen의 예약 토큰을 빌린다 (`<|fim_prefix|>` 등).
- 코드: [github.com/jaredpalmer/kev](https://github.com/jaredpalmer/kev) — `kev/api.py`, `kev/model.py`, `kev/serve.py`.

## 9. 브라우저 Kev — 잰 것 (2026-10-06)

코드와 절차: [`lab/kev-web/`](../../lab/kev-web/README.md). 이 PC: AMD RX 9070 XT (WebGPU, shader-f16), Ryzen 7 9700X. 모델 파일은 로컬 정적 서버에서 받았다 (네트워크 다운로드 시간은 빠졌다).

**변환** — onnx-community가 ONNX Runtime GenAI 도구로 만든 Qwen3.5-0.8B 그래프(Gated DeltaNet은 `LinearAttention`·`CausalConvWithState`, 전체 주의는 `GroupQueryAttention`)에 Kev 가중치(Qwen3.5-0.8B-Base + LoRA 병합)를 이름대로 갈아 넣었다. 320개 가중치가 전치·1+w·그대로·−exp(A_log) 넷으로 모두 대응했다. 출력층(임베딩을 공유)을 떼고 마지막 정규화의 출력을 은닉 상태로 낸다. 판정 헤드(1024 → 256 두 행렬, 온도 2.35)는 JS로 셈한다.

**정확도** — 기준: PyTorch Kev(fp32)의 확률. 세트: `lab/decide`의 48건(질문 3개씩) + 1단계 크기 요청 1건 = 질문 157개.

| 판 | 크기 | 최대 확률 차이 | 1순위 뒤바뀜 | 뒤바뀐 질문의 원래 1·2순위 차 | 질문 3개 | 1단계 크기 (질문 13개) |
|---|---|---|---|---|---|---|
| fp32 (onnxruntime CPU) | 3.1 GB | 0.00000 | 0 | — | 1.4초 (CPU) | 4.4초 (CPU) |
| **fp16** (WebGPU) | 1.54 GB | 0.019 | 4 | 0.003~0.011 (동률) | 0.23초 | 0.58초 |
| **q8** — 투영 8비트, 임베딩 fp16 | 1.07 GB | 0.042 | 11 | 모두 < 0.05 | 0.14초 | **0.40초** |
| q8 + 임베딩 4비트 | 0.71 GB | 0.085 | 24 | 최대 0.068 | 0.14초 | — |
| q4 — 투영 4비트, 임베딩 fp16 | 0.82 GB | 0.27 | 33 | 7개가 ≥ 0.05 | 0.14초 | — |
| q4 + 임베딩 4비트 | 0.46 GB | 0.25 | 29 | 최대 0.18 | 0.14초 | — |

- 토크나이저: 브라우저(transformers.js `Qwen2Tokenizer`)의 인코딩이 파이썬과 49/49 같다.
- 실행 방식 (질문 13개, fp16): 상태를 한 번 돌리고 질문 가지를 이어 돌리기(`prefix`) 0.58초 · 모든 줄을 한 번에(`batch`) 0.71초 · 줄마다 따로(`rows`) 0.93초. q8에서는 `batch` 0.40초 · `prefix` 0.43초.
  내부 상태(Gated DeltaNet의 상태·KV)를 GPU에 남기니(onnxruntime-web `preferredOutputLocation: 'gpu-buffer'`) 질문 3개가 1초 → 0.25초로 줄었다.
- 첫 실행은 셰이더 컴파일로 2~5초 더 걸린다. 모델 올리기(로컬 서버) 1~5초.
- 4비트 손실은 임베딩이 아니라 **투영 행렬**에서 온다 (투영만 4비트여도 뒤바뀜 33). 단순 반올림(RTN) 양자화의 결과라, 보정 데이터를 쓰는 방법(GPTQ·AWQ 등)이나 학습 뒤의 확신 있는 분포에서는 달라질 수 있다 — 잰 것은 아니다.
- 기성 Kev-0.8B는 한국어 뜻을 모른다: 1단계 크기 요청에서 "숲은 베지 마라"에도 나무 거두기를 "하라"로 냈다. 학습이 먼저다 (I3).

**판단** — 지금 기준으로 쓸 만한 판은 **q8 (1.07 GB, 질문 13개 0.4초)**. 크기를 더 줄이려면 학습한 모델로 양자화 방법을 다시 잰다. 이 수치는 고급 데스크톱 GPU 기준이라, 내장 그래픽에서는 몇 배 느릴 것이다 (안 잼).
