# 결정형 AI(Kev) 활용 검토 — 도메인 정보 위에서 (2026-10-07)

질문: 도메인 영역([INFO.md](INFO.md))을 바탕으로 결정형 모델 Kev를 어떻게 쓰면 잘 쓰는가.
해석기 설계의 진행 상태는 [INTERPRETER.md](INTERPRETER.md)에 있다(I1~I9 정함, O1~O6 열림). 이 문서는 그 위에 도메인을 대어 보고, 잰 것과 제안과 새로 정할 것을 남긴다.
**검토만 했다. 코드와 규칙은 바꾸지 않았다.**

> **뒤이은 실험 (같은 날)**: 이 문서는 Kev의 질문 꼴을 전제로 했다. 그 전제까지 열어 여러 방법을 실제로 잰 결과는 [AI-OPTIONS.md](AI-OPTIONS.md)에 있다 —
> 질문마다 모델을 돌리지 않고 **한 번 읽고 작은 판정기로 정하는 쪽**이 빠르고(0.05초 대 0.49초) 학습도 CPU로 된다. 이 문서의 투영·결정론·석판과의 나눔·정답 공장은 그대로 쓰인다.

## 0. 요약

1. **도메인이 Kev의 재료를 이미 만든다.** 상태는 대사제의 눈(`view(gameInfo, 'priest')`)이다. 선택지는 일의 종류(`KINDS`)와 그 일을 할 수 있는 칸(`legalActions` → `kindOf`)이다. 답을 받아 보여 줄 곳은 확인 화면(`previewInfo`)이다.
   남은 것은 두 가지다: Kev가 읽을 꼴로 바꾸는 얇은 층(**투영**)과, 해석기들이 함께 내는 **답의 계약**(`Intent`).
2. **대사제의 눈을 그대로 넣으면 길다.** 판을 빼도 중앙 521토큰이다. 필요한 것만 추리면 191토큰으로, 브라우저에서 잰 견본(206토큰, 질문 13개 0.4초)과 같은 크기가 된다 (§2).
3. **1단계는 "일마다 하라 / 하지 마라 / 말하지 않음"이 맞다.** 10-03 실험에서 결정형 모델은 금지를 따로 물으면 "관련 있는 일"을 꼽았다. 한 질문 안에서 하라와 하지 마라가 확률을 나눠 갖게 하면 그 실패를 질문의 구조가 막는다. 다만 **남는 손은 따로 묻는 줄이 하나 필요하다** (§4).
4. **Kev는 해석의 경계에만 둔다.** 엔진의 판정(되풀이, 율법파, 자동 계산)에는 넣지 않는다.
   이유: GPU·양자화마다 확률이 조금씩 달라 1순위가 뒤바뀐다(fp16 4/157, q8 11/157). 그러면 같은 시드가 기기마다 다른 판이 된다. Kev는 말할 때 한 번 부르고 답을 기록한다 (§5).
5. **가장 큰 쓸모는 "Kev가 풀고 석판이 배우는" 고리다.** 지금도 LLM이 알아들었는데 석판이 못 이은 낱말은 대사제의 말버릇(`lessons`)이 된다. 말버릇은 대사제의 눈에도 들어간다. Kev가 같은 자리에 서면, 은유는 Kev가 풀고 다음부터는 석판이 결정적으로 알아듣는다 (§6).
6. **학습이 먼저이고, 데이터 공장은 도메인 덕에 거의 공짜다.** 엔진으로 상태를 만들고, 게임과 같은 `view`·투영 함수로 입력을 만들고, 석판과 Gemma로 정답을 붙인다. 학습과 실행의 입력이 한 함수에서 나오니 어긋날 수 없다 (§7).

## 1. 도메인 → Kev 대응

| Kev가 필요한 것 | 도메인에서 | 상태 |
|---|---|---|
| 1단계 상태 ("무엇을") | `view(gameInfo(state), 'priest')`에서 판을 뺀 것 | 있음 — **투영 필요** (§2·§3) |
| 1단계 질문 | 일의 종류 12가지(`KINDS`), 할 수 있는 일(`us.legalKinds`, 중앙 9 · 최대 11) | 있음 |
| 손의 수 | `us.actions` | 있음 |
| 2단계 선택지 ("어디서") | `legalActions` → `kindOf`가 그 일인 칸 | 있음 — 후보 수는 §2 |
| 2단계 칸 글 | 대사제가 보는 칸 정보: 지형·특징·주인·건물·성벽·성지·붙인 이름 | 있음. `SEEN`이 절대 가치·활성도·수확을 이미 뺀다 — INTERPRETER §5의 "값이 새지 않게"와 같은 결론이다 |
| 2단계 상태 | 판에서 이름 붙은 사실(주인 있는 칸·성지·이름) + 율법파의 뜻(칸) | 있음 — 투영 필요 |
| 답의 꼴 | 일의 종류. 석판의 되풀이 서명(`planSig`)도 이미 "알아들은 일의 종류 집합"이다 (interpreter.js:580) | 타입 없음 → `Intent`를 더한다 (§8) |
| 보여 줄 곳 | `previewInfo`(칩의 득·승률·선공), 칩의 "명함 / 헤아린 손" | 있음 — Kev의 확률(배치 점수)을 더할 자리 |
| 대사제의 말 (문장 틀, I2) | 고른 일·칸(`tileName`)·금지·교리·확신도 | 재료 있음 |

## 2. 잰 것 — 상태의 길이, 질문 수, 후보 수

48판(4~7칸, 쉬움~어려움, 두 번째 판), 540장. Kev의 `render` 꼴(`키: 값` 줄)로 펴고 Kev-0.8B 토크나이저로 셌다.

| 상태 | 중앙 | 90% | 최대 |
|---|---|---|---|
| 대사제의 눈 전체 | 1813 | 2330 | 2717 |
| 판을 뺀 것 (지금 `view` 그대로) | **521** | 575 | 625 |
| 필요한 것만 — 사건 이름, 율법파의 뜻·대비·신도·마을·수도, 말의 층, 손의 수·할 수 있는 일·모자란 것 | **191** | 241 | 292 |
| (참고) 브라우저에서 잰 1단계 견본 (INTERPRETER §2) | 206 | | |
| 2단계: 이름 붙은 칸 사실 + 율법파의 뜻 | 282 | 690 | 961 |

2단계 후보 칸 수 (그 일을 할 수 있는 칸):

| 일 | 중앙 | 90% | 최대 |
|---|---|---|---|
| 마을 짓기 | 9 | 10 | 11 |
| 탐험 | 5 | 7 | 9 |
| 식량 거두기 | 4 | 6 | 8 |
| 선교 · 공격 | 3 | 7 | 9 |
| 나무 · 성벽 | 2 | 3~4 | 5 |
| 돌 · 신앙 거두기 | 1 | 2~3 | 4 |

**읽은 것**

- 지금 대사제의 눈을 그대로 펴면 소음이 많다. `id: schism` 같은 내부 이름, `gather:food` 같은 코드, `null`이 펴진 빈 줄(`quote: `), 빈 배열이 들어간다.
  율법파의 승점 항목·자원·수입·유지도 들어 있다. **INTERPRETER §2는 승점을 "전략 재료"로 뺐는데, `SEEN`은 율법파 쪽을 통째로 대사제도 보게 해 두었다 — 어긋남** (K1).
- 1단계에 칸 이름이 섞인다. 율법파의 뜻이 `kind + tile`이라서다. I6("1단계는 칸 정보 없음")과 어긋난다.
- 1단계 질문은 할 수 있는 일만이면 최대 11 + 교리 1, 12가지 모두면 13(+ 갈림길 1)이다. §9 실측(질문 13개, q8 0.4초)과 같은 규모다. 다만 그 실측은 206토큰 상태였다 — 521토큰이면 더 걸린다 (재지 않았다).
- 2단계 선택지는 최대 11로, Kev 한도(255) 안이다. 판이 커져도 후보는 닿는 칸이라 크게 늘지 않는다. 늘어나는 것은 2단계 **상태**(주인 있는 칸 사실, 최대 961토큰)다. 후보 칸에 걸린 사실만 남기면 줄일 수 있다.

## 3. 제안 — 층을 나눈다

```
state ─gameInfo→ 정보 객체 ─view('priest')→ 대사제의 눈        ← SEEN: 볼 수 있는 상한
                                   └─ 투영 (1단계용 · 2단계용)    ← 넣을 것만, Kev가 읽을 낱말로
                                          └→ Kev ─확률→ Intent ─칸 배정→ Placement ─validateOrders→ 확인 화면 · 문장 틀
```

| 층 | 하는 일 | 어디에 |
|---|---|---|
| `SEEN` | 누가 **볼 수 있나** (상한) | 도메인 (`seen.js`) — 그대로 |
| 투영 | Kev에 **넣을 것** — 허용 목록, 낱말, 순서 | 해석기 쪽 (예: `js/game/ai/`). 낱말은 언어팩(`kev.*`, O5) |
| `Intent` · `Placement` | 해석기들이 함께 내는 **답의 꼴** | 도메인 타입 (`types.d.ts`) |

**투영 규칙 (제안)**

- 내부 이름·코드는 이름으로 바꾼다. 예: `gather:food` → "식량 거두기".
- 비어 있으면 줄째 뺀다.
- 키 순서를 고정한다. Kev는 상태를 글로 읽으므로 순서가 바뀌면 입력이 바뀐다.
- 1단계의 율법파 뜻은 칸 대신 **대상**으로 적는다: 우리 땅 / 빈 땅 / 저들 땅. 그래야 "막아라"·"노리는 곳"을 칸 없이 알아듣는다.
- **투영 ⊆ `SEEN`**을 `info.mjs`가 검사한다. 대사제가 못 보는 것이 투영에 들어가면 위반이다.

**상태 꼴에 번호를 붙인다**

학습한 모델은 학습 때의 상태 꼴에만 맞는다. `SEEN`이나 투영을 바꾸면 다시 학습해야 한다. 그래서 `STATE_SCHEMA` 번호를 모델 파일과 함께 둔다.
같은 까닭으로 △ 항목은 **학습 데이터를 만들기 전에** 정해야 한다: 장 번호·막, 믿음의 표식, 지난 장에 한 일, 모자란 것(O4).

## 4. 제안 — 질문의 꼴 (O1·O2·O3 다시 보기)

**1단계: 일마다 3지선다 `하라 / 하지 마라 / 말하지 않음`** (INTERPRETER O1의 ⓑ)

- 근거: 10-03 실험([DECISION-MODELS](../DECISION-MODELS-2026-10-03.md) 관찰 2)에서 금지를 따로 물으면 결정형 모델이 "관련 있는 일"을 꼽았다. Kev-4B는 기본 10개 중 8개에서 명할 일을 금지 1순위로 꼽았다.
  하라와 하지 마라가 한 질문 안에서 확률을 나누면 "관련 있음"만으로는 답할 수 없고, 둘 중 하나를 골라야 한다.
- **할 수 없는 일도 묻는 쪽을 권한다** (K2). 할 수 있는 일만 물으면 줄이 2~3개 준다. 대신 "알아들었으나 할 수 없다"는 되먹임을 Kev가 낼 수 없다 — 지금은 석판의 `cannotWhy`와 확인 화면의 빨간 칩이 이 일을 한다.
  12가지를 모두 물으면 상태와 무관하게 낱말을 이해하는 법도 함께 배운다.

**남는 손: 줄 하나를 더 두기를 권한다** (K3)

- I5는 남는 손도 AI가 채우게 했고, O1은 "하라 확률 순으로 채운다, 남는 손 질문은 따로 두지 않는다"였다.
- 걸리는 점: 학습에서 말하지 않은 일은 모두 "말하지 않음"이 정답이다. 그 안의 하라 확률은 학습 목표가 없는 잔여값이라, 그것으로 줄을 세우면 무작위에 가깝다.
- 그래서 `남는 손은 무엇에 쓰는 것이 이 계시의 뜻에 맞나?`를 선택지 한 줄로 둔다(할 수 있는 일 중 하나). 정답은 Gemma가 실제로 채운 손에서 온다. 질문이 13 → 14줄로 는다.
- 이 줄의 상태(특히 모자란 것, O4)가 I5에서 짚은 "남는 손의 똑똑함" 손잡이가 된다. 난이도마다 다르게 넣을 수 있다.

**나머지**

| 것 | 제안 |
|---|---|
| 같은 일 여러 손 | 일의 종류 질문은 수를 모른다. "두 곳", "모두"는 석판에 남긴다 (INTERPRETER §5). 말이 없으면 명한 일 하나에 한 손이다. 같은 일이 남는 손으로 다시 뽑히면 2단계의 2순위 칸으로 간다 |
| 문턱 (O2) | 명한 일 = 하라가 1순위이고 p ≥ θ. θ는 학습 뒤 검증 세트에서 정한다 — 지금 숫자를 박지 않는다. 확인 칩의 "명함 / 헤아린 손", 판결, 되풀이가 이 구분을 쓴다 |
| 2단계 (O3) | 고른 일마다 그 일의 칸 선택지 한 줄. 채운 손도 Kev가 고른다 — 확률이 곧 배치 점수다. "한 칸에 한 가지" 충돌은 확률 큰 쪽부터 배정한다 |
| 선택지 순서 | Kev는 순서에 흔들린다. 실행 때는 칸 id 순으로 고정하고(결정론), 학습 때는 순서를 섞어 둔감하게 만든다 |
| 갈림길 | 사건에 두 갈래가 있으면 `A / B / 말하지 않음` 한 줄 (`eventInfo.choice`가 선택지 글을 준다). 지금 정규식 `dilemmaByText`의 자리다 |
| 말투 | 같은 방식으로 `TONES` 선택지 한 줄을 둘 수 있다. 지금은 정규식 `detectTone` |

## 5. Kev를 두지 않을 곳 — 결정론

| 곳 | 왜 | 대신 |
|---|---|---|
| 엔진의 판정: 되풀이 서명(`planSig`), 율법파의 계획, 자동 계산 | 기기마다 확률이 조금씩 달라 거의 동률에서 1순위가 뒤바뀐다(§9: fp16 4/157, q8 11/157). 같은 시드가 기기마다 다른 판이 되면 오늘의 계시·도전장·golden·퍼징이 무너진다 | Kev는 말할 때 **한 번** 부르고 답(`Intent`·`Placement`)을 기록한다 |
| 되풀이 서명의 출처 (K4) | 지금 서명은 석판이 알아들은 일의 종류 집합이다. 계시를 쓰는 동안 비용 알약이 키 입력마다 셈한다 | ⓐ 석판 그대로 (권: 결정적이고 미리 셀 수 있다) · ⓑ Kev의 하라 집합을 말할 때 정해 저장 (`spokenOf`가 이미 말할 때 서명을 저장한다). ⓑ면 쓰는 동안 보이는 되풀이 +1이 실제와 다를 수 있다 |
| 쓰는 동안의 예감 (K5): 알아들은 말 줄, 다음 장 율법 카드 예고, 판 위 힌트, 계시 제안 | 키 입력마다 돈다. Kev는 질문 13개에 0.4초(고급 GPU)이고, 내장 그래픽에서는 몇 배다 | 석판에 남긴다(지금 그대로). 또는 입력이 멈출 때 한 번(디바운스). 석판 예감과 Kev 답이 다를 수 있으니 화면은 "예감"이라 말한다 |
| 시험 도구 | 퍼징·golden은 모델 없이 돈다 | Kev 회귀는 따로: 고정 세트의 답을 파일로 남겨 견준다 (`lab/prompt-snap.mjs`와 같은 방식) |

## 6. 석판과 나누기 — 그리고 배우는 고리

| 일 | 석판 (글자·규칙) | Kev (뜻) |
|---|---|---|
| 정확한 지목: 칸 이름, 붙인 이름, "E4 말고" | 맡는다 | — |
| 수: 두 곳, 모두 | 맡는다 | — |
| 활성도 낱말: 기름진 곳, 쉬던 땅 | 맡는다 | — |
| 신만 하는 일: 기적·계명·예언·이름 (`parse*`) | 맡는다 (그대로) | — |
| 명백한 부정 "~하지 마라" | 확실하다 | 배운다. ~~둘이 다르면 석판을 따른다~~ — 쟀더니 이득이 없어 거뒀다 ([AI-OPTIONS §3.4](AI-OPTIONS.md#34-금지와-정답-보강)) |
| 은유·문맥 ("겨울이 온다", "손을 펴라") | 못 한다 | **맡는다** |
| 일의 종류·교리 | 대조용 | 맡는다 |
| 낱말 ↔ 일 잇기 (밑줄·빛줄기·판결 낱말) | `linkWords` | 낱말 위치를 모른다 |

**낱말 잇기**: Kev는 어느 낱말이 그 일을 불렀는지 말하지 않는다. 지금 LLM 답도 같은 처지이고, 석판의 `linkWords`를 LLM이 고른 일에 대해 돌려 밑줄을 긋는다 (main.js:605). Kev도 그대로 쓰면 된다 — 석판이 못 잇는 은유 일만 밑줄이 없다.

**배우는 고리 (권하는 쓰임)**

- 지금: LLM이 알아들었는데 석판이 못 이은 낱말은 대사제의 말버릇(`extractLesson`)이 된다. LLM 출처일 때만 배운다 (main.js:755).
- 말버릇은 석판이 다음부터 알아듣는 규칙이 된다. 동시에 대사제의 눈에도 들어간다 (`us.lessons`는 대사제도 본다).
- Kev 출처에도 같게 하면: 은유는 Kev가 풀고, 석판이 배워 다음부터 결정적으로(빠르게, 기기와 무관하게) 알아듣는다. 쓰는 동안의 예감도 그만큼 정확해진다. §5의 결정론 문제를 판이 갈수록 줄이는 길이다.

**확신도가 낮을 때 (O6)**: 하라 1순위가 문턱 아래이고 석판도 못 알아들으면, 대사제가 "말씀이 흐릿하다"고 하고 남는 손 질문으로 채운다. 석판으로 넘기는 것은 석판이 알아들었을 때만 뜻이 있다.
